# HEARTH — The local agent loop, and the ceiling it is built against

**Status:** Implemented and tested (`src/hearth/agent/`, 124 tests, all offline). Not yet wired
to the CLI or the gateway — it is a library a caller assembles deliberately.
**Date:** 2026-09-02.
**Scope:** the tool protocol, prompt-based tool calling on local weights, the bounds and how
they surface, the audit transcript, the security model, how to add a tool, and — at length —
what this deliberately does not do.
**Constraint:** nothing here adds a byte of network capability to HEARTH.
`tests/test_agent_no_network.py` enforces that over the package's own source, in the pattern
`tests/test_handoff_no_network.py` established. See `docs/TIERS.md`.

---

## 0. TL;DR

`hearth.agent` gives the operator a way to hand HEARTH a task over their own local data — *"which
of these statements covers March, and what did it total?"* — and have a local 3B–14B model work
it out in steps, with no cloud model anywhere in the path.

It plans, calls **one** tool, observes the result, and repeats, until it answers or hits a
bound. Every run returns an `AgentRun` carrying the full transcript and a `stopped_reason`. The
result type **cannot hold an answer unless the model actually answered**, so an exhausted budget
can never be read as a conclusion.

The honest summary of what it is for:

> **Bounded steps: yes. Long-horizon autonomy: no.**

---

## 1. The capability ceiling, stated first

A 3B–14B model running 4-bit on this machine is genuinely good at one thing and genuinely bad
at another, and pretending otherwise is how you ship something that looks autonomous and quietly
produces garbage.

**What it does well.** One well-specified step at a time. *Pick the file whose name matches
March. Read it. Pull the total out of the ledger. Say what the passage says.* Each step is
individually checkable, and the model is choosing between a handful of clearly-described tools
rather than composing a plan from nothing.

**What it does badly, and does not get better at with more iterations:**

- **Noticing that its plan stopped working.** It will re-issue a call that already failed, with
  the same arguments, confidently. This is why consecutive failures terminate the run rather
  than being retried forever.
- **Recovering from a partial result.** Given three of five files, it will answer as if it had
  five. This is why every truncation — of its own output, of a tool observation, of a listing —
  is *marked in the text the model reads*, and why an incomplete finance figure carries
  `INCOMPLETE` in the field the model is looking at.
- **Long chains.** Error compounds. By step eight, a small model is usually reasoning about
  a hallucinated version of step three. The default `max_iterations` is 8 and that is a
  ceiling, not a target: a task needing thirty steps is a task that needs decomposing.
- **Knowing when it does not know.** Its most likely output for an unanswerable question is a
  fluent, specific, wrong answer. Nothing in this loop fixes that. What the loop does is make
  the answer *traceable*, so a wrong one is visibly unsupported by its own steps.

So the design target is not "an agent that finishes anything". It is **an agent that either
finishes a bounded task or stops and says exactly where it got to** — the only two outcomes that
are useful to an operator who has to trust the result.

### 1.1 Why arithmetic and verification stay in Python

`CLAUDE.md` §4: *financial arithmetic is Decimal in Python, never a model and never a float.*
The agent inherits that without exception, and it generalises past finance.

A model may **decide** and **describe**. It must not **compute** and it must not **verify**.

- The `finance_total` tool returns a number the ledger computed by summing an integer column in
  SQL *and* re-adding the canonical decimal strings in Python, refusing to return anything if
  the two disagree (`hearth.finance.store`). The model sees a finished figure. It is told, in
  the tool description it reads every turn, *"the ledger does the arithmetic — never add these
  figures up yourself."*
- `finance_explain` exists so a figure that reaches the operator arrives with every row behind
  it and a running sum. That listing is generated by `store.explain()`, not by the model.
- The `read_file` tool refuses a scanned PDF with no text layer rather than returning an empty
  string, because a model handed a blank document writes a confident summary of nothing
  (`hearth.mcp.files`). Refusal is a verification the model cannot perform on itself.

The rule underneath all three: **a check must assert on the outcome, never on a configuration
that implies the outcome** (`CLAUDE.md` §3). A model asserting that its own answer is right is
the purest form of a check and its subject being the same object. So verification lives in
Python, in the tools, or in the operator reading the transcript — never in an extra turn where
the model grades itself.

## 2. The design

Four modules, all in `src/hearth/agent/`.

| Module | What it owns |
| --- | --- |
| `tools.py` | `Tool`, `ToolParam`, `ToolRegistry` — declaration, registration, and argument validation *before* dispatch. |
| `protocol.py` | The output contract, the system prompt, and the strict parser. |
| `loop.py` | `Agent`, `Budget`, `Step`, `AgentRun` — the loop, the bounds, the transcript. |
| `builtins.py` | The vetted read-only tools: files, RAG, ledger. |

### 2.1 One turn

```
system prompt (role + tools + contract + task)
user: "Begin."
    -> model emits ONE JSON object
    -> parse (strict)                    -> unparseable? feed the reason back
    -> look the tool up                  -> unknown?     feed the list back
    -> validate arguments vs the schema   -> mismatch?    feed the parameter back
    -> dispatch                          -> raised?      feed the refusal back
    -> render observation (truncation marked)
user: "Observation from <tool>: ..."
    -> repeat, until an answer or a bound
```

Every arrow labelled *feed back* is a **recoverable** turn: recorded in the transcript, handed
to the model as its next observation, and never a crash and never a silent skip. The one thing
the loop will not do is invent a step or synthesise an answer.

### 2.2 The output contract

The model must reply with exactly one JSON object:

```json
{"thought": "why this step", "tool": "read_file", "arguments": {"path": "/notes/march.txt"}}
{"thought": "why this is enough", "answer": "March totalled 120.50"}
```

**Strict where ambiguity is dangerous.** Refused outright: no JSON object at all; *more than
one* JSON object; both `tool` and `answer`, or neither; `arguments` that is not an object.
Two objects are refused rather than taking the first, because taking the first is how an agent
quietly skips the step it told you it took.

**Forgiving where strictness would only cost iterations.** Absorbed silently: markdown fences,
a `<think>` block, a `<tool_call>` wrapper, prose around the object, the `name`/`parameters`
spellings, and `arguments` delivered as a JSON *string*. None of those change which action was
requested.

### 2.3 Tool calling on local weights — what was actually found

**mlx-lm 0.29.1 does have native tool-call machinery, and it is not reachable from here.**

The measurement:

- `mlx_lm.server` implements tool calling: it passes `tools=` through
  `tokenizer.apply_chat_template`, then watches the generated token stream for
  `tokenizer.tool_call_start` / `tool_call_end` and `json.loads` the text between them into
  `{"name": ..., "arguments": ...}`.
- `TokenizerWrapper` sets those sentinels only when the tokenizer's chat template mentions
  `"tool"` **and** `<tool_call>`/`</tool_call>` are in the vocabulary.
- The installed weights do qualify. `~/.hearth/models/…Qwen2.5-3B-Instruct-4bit` declares both
  tokens as added tokens and its chat template is tool-aware.
- **But it lives in the HTTP server, not in `mlx_lm.generate`**, and HEARTH's provider contract
  has no seam for it: `GenRequest` has no `tools` field and `GenResult` has no `tool_calls`
  (`src/hearth/providers/base.py`). Wiring it would mean changing every provider, and the
  capability would then exist only for models whose tokenizer happens to declare those tokens —
  present on Qwen2.5, absent on the next model, invisible at the call site either way.

So: **prompt-based tool calling**, deliberately shaped to emit and accept *the same payload*
mlx-lm's native parser produces. A model that has been trained to emit a native `<tool_call>`
block parses here unchanged (`tests/test_agent_protocol.py`), and if a `tools` field ever lands
in the provider contract, the wire shape does not have to move.

### 2.4 The bounds, and how they surface

`Budget` (all enforced, all with their own stop reason):

| Bound | Default | Stop reason |
| --- | --- | --- |
| `max_iterations` | 8 | `max_iterations` |
| `max_seconds` | 180 | `timeout` |
| `max_total_tokens` | 24 000 | `token_budget` |
| `max_consecutive_invalid` | 3 | `invalid_output` |
| `max_step_tokens` | 768 | (per-generation cap; a hit is a *truncated turn*, not a stop) |
| `max_observation_chars` | 4 000 | (per-observation cap; truncation is marked in the text) |

Plus two terminal failures that are not budgets: `provider_error` (the backend could not
generate) and `egress_refused` (§4).

Three properties matter more than the numbers:

1. **Bounds are checked before each model call**, so a run never starts a step it cannot pay
   for, and the reported totals are what was actually spent — not what was budgeted.
2. **`max_total_tokens` counts prompt *and* completion across every step**, including the
   transcript re-sent each turn. That is where an agent's cost actually goes; a budget that
   ignores it does not bound anything.
3. **The stop reason is part of the result type.** `AgentRun.__post_init__` refuses to
   construct a run that stopped for any reason other than `answered` while carrying an answer,
   *and* refuses an `answered` run with no answer. The impossible state cannot be built, so no
   caller has to remember to check a flag before reading a field. `require_answer()` raises
   `AgentIncompleteError` naming the stop reason.

This is the `finish_reason: "stop"` lesson from `gateway/app.py` (`CLAUDE.md` §3) applied to a
whole run instead of one generation: there, a default of `"stop"` hid a truncation at 512
tokens. Here, there is no default — the reason is a required constructor argument and it
constrains what else the object may hold.

### 2.5 The transcript

`AgentRun.transcript()` renders the headline *and* the evidence, in the shape of
`FinanceStore.explain()`: the reader sees whether the conclusion is supported rather than being
told that it is. Each `Step` carries the model's raw output, the parsed thought, the tool, the
validated arguments, the observation or the error, the model and backend that served it, token
counts, and separate model/tool timings. An unanswered run's transcript ends with:

```
  NOT AN ANSWER — this run stopped before the model concluded. Anything above is a
  partial trace, not a result.
```

**An agent's conclusion that cannot be traced to its steps is a claim, not a result.**

## 3. The built-in tools

Each is a thin wrapper over a gate that already exists, so the agent inherits that gate rather
than acquiring a second copy of it.

| Tool | Goes through | Therefore governed by |
| --- | --- | --- |
| `read_file(path)` | `hearth.mcp.files.read_text_file` | `HEARTH_FILE_ROOTS`, deny-by-default, symlink resolution, size cap, format table |
| `list_files(root, pattern)` | `allowed_roots` + `resolve_under_roots` | the same allowlist, re-checked on every resolved path |
| `rag_search(query, collection, k)` | the caller's `RagIndex` | whatever that index was built over |
| `finance_total / finance_explain / finance_rows` | the caller's `FinanceStore` | Decimal arithmetic, the two-sum integrity check, exclusion reporting |

`rag_search` deliberately calls `query(..., answer=False)`. Letting the tool answer would hide a
second model call inside one step: its tokens off the agent's budget, its reasoning out of the
transcript, and the agent then reasoning over a summary of a summary. The agent is the reasoner;
the tool hands it passages and their sources.

`list_files` exists so a path in a transcript came from the filesystem rather than from the
model's imagination. With only `read_file`, a small model guesses filenames — plausibly, and
wrongly.

### 3.1 Why there is no write tool

**A wrong read and a wrong write are not comparable failures.**

A wrong read produces a wrong sentence, and the transcript shows exactly which observation it
rests on — the operator can check it in ten seconds. A wrong write produces a corrupted file, a
mis-categorised ledger row, or a deleted note, *and the agent reports it as done*. There is no
transcript reading that undoes it.

That asymmetry does not shrink as models improve; it is a property of the operation, not of the
model. So writes stay out of the default set as a **standing decision**, not an oversight, and
`tests/test_agent_no_network.py` fails if `write_text`, `mkdir`, `unlink` or friends appear
anywhere in the package. If a write agent is ever wanted, it needs its own document, its own
review, and — at minimum — a dry-run mode whose diff a human approves before anything lands.

The same reasoning excludes a shell tool. A shell is not one capability; it is every capability,
including egress, and it would make the no-network invariant unprovable in a single line.

## 4. The security model

Four layers, each asserting on a different thing.

**1. Capability is injected, never discovered.** `ToolRegistry` starts empty. There is no
entry-point scan, no plugin hook, no ambient default toolset. `Agent(...)` refuses to construct
with no tools at all. *"What can this agent reach?"* is answered by reading one call site.

**2. Tool code must live in `hearth.agent`.** `vetted_only=True` (the default) admits only tools
whose callable's `__code__.co_filename` resolves inside `src/hearth/agent/`. A caller who needs
their own tool passes `vetted_only=False` — one greppable word, and a documented transfer of
responsibility.

> **Why by code location and not by an allowlist of tool names.** A name is a label the caller
> chooses. `Tool(name="read_file", call=fetch_url)` passes a name allowlist perfectly: the check
> and the checked thing would be different objects, which is precisely the bug class
> `CLAUDE.md` §3 catalogues. `__code__.co_filename` says where the body was *compiled from*, and
> the source at that location is mechanically proven network-free by the AST test. A C function
> or builtin has no `__code__` and is refused for that reason alone — there is no source for the
> invariant to be proven over.
>
> **What this bounds and what it does not.** It bounds the tool *code*. It does not bound an
> object a built-in tool was constructed with: a fake `RagIndex` that phoned home would still
> phone home, because the agent package never sees inside it. That is the caller's
> responsibility, and it is stated here rather than papered over.

**3. No network in the package, enforced by AST over its own source.**
`tests/test_agent_no_network.py`, following `tests/test_handoff_no_network.py`:

- imports are allowlisted — a tiny stdlib set with **no transport**, plus exactly three HEARTH
  modules (`hearth.mcp.files`, `hearth.providers.base`, `hearth.router.route`);
- **relative imports are resolved, not skipped.** This is the one place this test departs from
  the handoff original, and it is the largest hole available: `from ..providers.remote import
  RemoteProvider` is a relative import, and that module is the only one in this repository that
  can open a socket. It is named in the failure message;
- no shell, dynamic-import or socket names appear as calls;
- no non-docstring string literal contains `://`, so an endpoint cannot be smuggled in as data;
- and a separate test asserts the package imports nothing from `hearth.providers` except `base`,
  so generations cannot bypass the router.

The convenience that would break this is *"just fetch that page for me."* The test is there so
that lands as a red build.

**4. Local by outcome, not by configuration.** Every generation goes through
`Router.route(..., allow_escalation=False)` — and then the loop **checks what actually
happened**: `decision.backend` and `record.served_by` must both say `local`, or the run ends
with `stopped_reason == "egress_refused"` and the offending step is in the transcript.

Asserting on the flag we passed in would be checking our own request rather than the outcome. A
policy edit, a future backend that ignores the flag, or a plain bug would each give a quietly
remote agent while every configuration still read "local". That is entry ten in the
`CLAUDE.md` §3 table, and this is the gate that prevents it.

## 5. Using it

```python
from hearth.agent import Agent, Budget, local_toolset

agent = Agent(
    router,                                        # a hearth.router.Router
    local_toolset(settings=settings, finance=store),
    budget=Budget(max_iterations=6),
)
run = agent.run("What did groceries total in March 2026?")

print(run.transcript())        # always — every step, whatever happened
if run.completed:
    use(run.require_answer())  # raises if the run stopped short
else:
    report(run.stopped_reason, run.detail)
```

`local_toolset()` includes the file tools always (they gate themselves on `HEARTH_FILE_ROOTS`,
which may well be empty — then the agent can read nothing and says so) and adds RAG or finance
tools only when the collaborator is passed. An agent's reach is decided by what the caller
constructed, not by what happens to be installed.

Temperature defaults to **0**: the contract asks for one exact JSON shape, and sampling noise
buys nothing but parse failures.

### 5.1 How to add a tool

```python
from hearth.agent import Tool, ToolParam

def word_count(path: str) -> int:
    """Count words in an allowlisted file."""
    return len(read_text_file(path, settings=settings).split())

Tool(
    name="word_count",                       # lowercase snake_case; matched verbatim
    description="Count the words in one local file.",   # an instruction, not a label
    call=word_count,
    params=(
        ToolParam(
            name="path",
            type="string",                   # string | integer | number | boolean only
            description="Absolute path, exactly as list_files reported it.",
        ),
    ),
    returns="a single number",               # so the model can plan the step after it
)
```

Then decide where it lives:

- **Inside `src/hearth/agent/builtins.py`** — it is covered by the AST invariant and passes
  `vetted_only=True`. This is the right home for anything general.
- **Outside** — the caller passes `vetted_only=False` and takes responsibility for it. Do this
  knowingly.

Four rules for a tool that a 3B model can actually use:

1. **Flat scalar parameters.** No nested objects, no arrays — a small model gets them wrong
   every third turn. A tool that needs structure wants several flat parameters instead.
2. **Descriptions written as instructions.** They are the only thing the model has to go on, and
   they are re-rendered into the prompt every turn. `ToolParam` refuses an empty one.
3. **Bound your output.** A tool that can return a megabyte will consume the whole budget in one
   step. Cap it *and say in the returned text that you capped it* — see `list_files`.
4. **Refuse rather than widen.** `_filters()` in `builtins.py` rejects an unparseable date
   instead of dropping it, because dropping `start` silently widens the query to the whole
   ledger and returns a much larger number that looks exactly as plausible.

## 6. What this deliberately does not do

- **No writes, no shell, no network.** §3.1 and §4. Standing decisions with tests behind them.
- **No self-verification turn.** Asking the model to grade its own answer is a check whose
  subject is itself. Verification is in Python, in the tools, or in a person reading the
  transcript.
- **No planning phase.** A local model asked to plan first produces a plausible plan it then
  fails to follow, and the plan becomes a second thing to hallucinate against. One step at a
  time, each grounded in a real observation.
- **No parallel tool calls.** One per turn, so every claim has exactly one result behind it and
  the transcript is a sequence rather than a graph.
- **No retry of a failed call with the same arguments.** The error goes back to the model and
  the model decides. Three consecutive failures end the run.
- **No memory across runs.** Each `run()` starts clean. Persisting agent state would create a
  store nothing audits.
- **No escalation, ever.** Not to PCC, not to a frontier model. If a local model cannot do it,
  the run stops and says so; the human-carried alternative is `src/hearth/handoff/`
  (`docs/TIERS.md`).
- **Not wired to the CLI or gateway.** Exposing this over HTTP means deciding who may pass
  `vetted_only=False` and what a hostile task string can reach through the tools. That is a
  separate decision and it has not been made.

## 7. Open questions

1. **Is prompt-based tool calling measurably worse than native on the installed weights?**
   Unmeasured. It would need an eval set of tasks with known-correct tool sequences, scored at
   temperature 0 against the promotion gate's rules (`CLAUDE.md` §7). Until that exists, no
   claim is made about which is better — only about which is *available* (§2.3).
2. **What is the real ceiling on step count for the 3B and the 14B?** The default of 8 is a
   judgement, not a measurement. The same eval set would settle it, per model.
3. **Should a failed run emit a handoff envelope?** A run that stops at `max_iterations` is
   exactly the "local tiers were insufficient" story `hearth.handoff` wants
   (`docs/TIERS.md` §4). The transcript is nearly the envelope's `LocalAttempt` already. Not
   wired, because it should not be automatic.
4. **What does a write agent need?** At minimum a dry-run diff a human approves. Not started.
